# Internationalisation — architecture et reste à faire

## Les deux axes de langue

Le point qui structure tout. **Deux langues indépendantes**, jamais déduites l'une de l'autre :

| | Colonne | Valeurs | Qui la voit |
|---|---|---|---|
| **Interface recruteur** | `users.ui_locale` | `fr` `en` | le recruteur, dans le dashboard |
| **Offre + parcours candidat** | `jobs.experience_locale` | `fr` `en` `nl` | le candidat, de bout en bout |

Un client néerlandophone qui travaille en anglais a `ui_locale = en` et publie des offres en `nl`.

**Une offre = une langue**, choisie à la création. Le contenu de l'expérience est *généré puis stocké rédigé* dans cette langue (`experience_steps.title`, `.prompt`, `.criteria`). Un trigger (`trg_jobs_langue_figee`, migration 026) **refuse** de changer la langue dès qu'une expérience existe : la changer ne réécrirait pas les textes déjà générés, et produirait un parcours mi-néerlandais mi-français.

## Où vit quoi

```
src/lib/i18n/
  config.js          locales, libellés, coercition, nom du cookie et de l'en-tête
  I18nProvider.js    contexte client, useT(), tNodes()
  navigation.js      Link / useRouter qui conservent le préfixe de langue
  actions.js         loadDictionary() — bascule de langue en cours de page
  actions-user.js    setUiLocale() — écrit users.ui_locale + cookie
  server.js          resolveUiLocale() — en-tête URL > cookie > Accept-Language > fr
  format.js          dates, montants, tri (remplace les toLocaleDateString("fr-FR"))
  prompt.js          consignes de langue injectées dans les prompts IA
  dictionaries/
    fr/  common.js  dashboard.js  candidate.js     ← SOURCE DE VÉRITÉ
    en/  common.js  dashboard.js  candidate.js
    nl/  common.js               candidate.js     ← pas de dashboard NL (voulu)
```

## Routage : préfixe côté recruteur, token côté candidat

```
app/
  layout.js                  ← layout racine unique : <html lang>, provider "common"
  [lang]/                    ← /fr/… /en/…
    layout.js                ← valide la locale, charge "dashboard"
    (dashboard)/  (auth)/
  apply/ assessment/ interview/ run/ join/   ← SANS préfixe
  api/  auth/callback/
```

**Le dashboard et l'authentification sont préfixés** : `/fr/jobs`, `/en/jobs`. Une URL préfixée est autoritaire — `/en/jobs` s'affiche en anglais même si le cookie du visiteur dit « fr ». C'est ce qui rend un lien partageable.

**Le parcours candidat ne l'est pas**, pour deux raisons :

1. ces liens sont **déjà partis par e-mail** ; les préfixer les casserait tous ;
2. la langue d'un parcours n'est pas un choix du candidat — les énoncés sont *stockés* rédigés dans la langue de l'offre. Un `/nl/run/xyz` laisserait croire qu'on peut basculer l'évaluation en français : l'interface changerait, les questions non.

### Mécanique

- **`src/proxy.js`** — redirige (307) tout chemin recruteur non préfixé vers `/{locale}/…`, en choisissant : cookie > `Accept-Language` > `fr`. Il pose ensuite l'en-tête `x-onbord-locale`, lu par `app/layout.js` qui est au-dessus du segment `[lang]` et ne peut donc pas lire `params`.
- **`lib/i18n/navigation.js`** — `LocaleLink` et `useRouter` préfixent les chemins internes. Sans eux, un `router.push("/jobs")` depuis `/en/jobs/123` perdrait la langue de l'URL à chaque clic.
- **`stripLocale()`** — à utiliser dès qu'on **compare** un `usePathname()` à un chemin littéral (onglets actifs de la sidebar et de `/compte`). C'est le piège classique du préfixe : sans lui, aucun onglet ne s'allume.

Le layout racine reste unique : `[lang]` est un segment *sous* lui, pas un paramètre racine. `next/root-params` ne s'applique donc pas — c'est voulu, ça évite d'avoir à déplacer le parcours candidat sous un second layout racine.

### Chargement par namespace

Chaque zone charge son namespace dans **son propre layout serveur**, et les providers s'imbriquent en fusionnant leur dictionnaire :

- `app/layout.js` → `common`
- `app/(dashboard)/layout.js` → `+ dashboard`
- `app/run/[token]/layout.js`, `apply/`, `assessment/`, `interview/` → `+ candidate`

Sans ce découpage, un candidat sur mobile téléchargerait les ~1 100 chaînes de l'interface recruteur qu'il ne verra jamais.

La locale du parcours candidat n'est connue qu'après chargement de l'offre : la page appelle alors `setLocale(job.experience_locale, ["common", "candidate"])`.

## L'IA

**Les prompts restent en français.** Ils sont longs, finement calibrés, et portent des garde-fous durement acquis. Le modèle lit du français et rédige en néerlandais sans difficulté : on ajoute une consigne de langue en tête de prompt, rien d'autre.

Deux langues de sortie distinctes :

- **contenu de l'expérience** (énoncés, QCM, ancres BARS, scénarios CRM) → langue du **candidat** ;
- **rapport de scoring** (justifications, synthèse) → langue du **recruteur**. C'est un outil de décision interne.
- **exception** : le `verbatim` n'est jamais traduit. C'est une citation exacte, contrôlée par `verifyVerbatim()` ; traduite, elle serait rejetée à tort.

### Trois langues de sortie, pas deux

`lib/i18n/prompt.js` expose trois consignes, une par destinataire :

| Helper | Destinataire | Langue | Utilisé par |
|---|---|---|---|
| `consigneLangueContenu(locale)` | le candidat | `jobs.experience_locale` | `lib/experienceGeneration.js` |
| `consigneLangueRapport(uiLocale, contentLocale)` | le recruteur qui lit un rapport | `users.ui_locale` | `lib/runScoring.js` |
| `consigneLangueConversation(uiLocale)` | le recruteur qui conçoit | `users.ui_locale` | `app/api/chat/assessment/route.js` |

Le troisième porte une subtilité que les deux autres n'ont pas : le chat produit aussi des **entrées d'outil** (`brief`, `consigne`) qui repartent vers les prompts de génération, eux en français. La consigne demande donc de dialoguer en anglais mais de rédiger ces deux champs en français. Sans cette séparation, un recruteur anglophone injecterait un brief anglais dans un prompt français : ça marche, mais le calibrage du générateur dérive sans qu'on puisse le constater.

## Vérification

```bash
node scripts/check-i18n.mjs
```

Contrôle six choses que ni le build ni ESLint ne voient :

1. toute clé de `fr/` existe dans `en/` et `nl/` ;
2. les marqueurs `{company}` survivent à la traduction ;
3. aucun composant n'appelle `t()` sans l'avoir déclaré (*ReferenceError au premier rendu*) ;
4. aucune clé appelée n'est absente des dictionnaires (*la clé brute s'afficherait à l'écran*) ;
5. aucun `t()` enfermé dans une chaîne — `placeholder="{t(…)}"` ou `cond ? "a" : "{t(…)}"` : le second cas est une **erreur de syntaxe que Turbopack a laissé passer une fois** ;
6. le contrôle 3 se fait **fonction par fonction**, pas fichier par fichier : un composant fautif était couvert par un voisin correct dans le même fichier — 6 ReferenceError sur la fiche offre sont passées comme ça.

À brancher en pre-commit ou en CI.

## Les e-mails candidats ne passent pas par `t()`

`lib/emails/templates.js` embarque les trois langues et se choisit sur `jobs.experience_locale`. Raison : `t()` rend dans la langue de l'**interface**, or ces messages sont lus par le **candidat**. Un recruteur en dashboard anglais qui écrit à un candidat néerlandophone doit obtenir un brouillon en néerlandais — la fenêtre le lui dit explicitement, sans quoi il croirait à un bug.

Les jetons `{{…}}` sont passés en anglais neutre (`{{candidate_first_name}}` au lieu de `{{prénom_candidat}}`) : des marqueurs français au milieu d'un e-mail néerlandais étaient illisibles pour le recruteur. Ils ne sont jamais persistés, le changement ne casse rien.

### Le motif à reproduire : valeur stockée ≠ libellé affiché

Trois endroits appliquent la même règle, et tout nouvel écran devrait la suivre :

```js
// La catégorie est stockée en base sous sa clé courte : seul le libellé suit
// la langue du recruteur. Une catégorie inconnue retombe sur sa valeur brute.
const CATEGORIES = ["cognitif", "langue", "metier", "personnalite", "ia"];
…
{CATEGORIES.includes(test.category)
  ? t(`dashboard.skillsTestConfig.categories.${test.category}`)
  : test.category}
```

Idem pour les catégories d'entretien vidéo (`CLES_CATEGORIES`) et les langues exigées par l'offre (`CLES_LANGUES` dans `JobFormStep2`) : la valeur qui part au moteur de recommandation et au prompt de scoring reste française, l'affichage suit le recruteur, et une valeur saisie à la main passe telle quelle.

## Deux pièges rencontrés, à connaître

**`perl -pi -e` mange les `${…}`** dans les remplacements : `t(\`…${axe}\`)` est devenu `t(\`…\`)` en silence. Le contrôleur l'a rattrapé (clé inconnue), mais préférez l'édition manuelle sur les template literals.

**Une variable locale nommée `t`** masque la fonction de traduction — ça arrive dans les `.map((t) => …)`. Rencontré trois fois (éditeur d'expérience, fenêtre d'e-mail). Renommer la variable, pas la fonction.

**Un effet qui appelle `t()` gagne une dépendance.** `t` change d'identité quand la langue change. Dans un effet qui *écrit* (recharger un fil de conversation, poser une locale), l'ajouter aux dépendances relance l'effet au changement de langue — au mieux un appel inutile, au pire une boucle (`/apply`, où `setLocale` est appelé dans l'effet lui-même) ou l'écrasement d'un message en cours de frappe (`AssessmentChatCreator`). Ces deux-là portent un `eslint-disable-next-line` commenté. Pour un effet en lecture seule et idempotent (`/join`), ajouter `t` est la bonne réponse : le message d'erreur se retraduit.

**Un `console.error` n'a pas besoin de `t()`.** Le traduire crée une dépendance de hook pour rien et un message que personne ne lit dans sa langue. Les préfixes de log restent en français.

**Le périmètre de mesure a un angle mort.** Les commandes ci-dessous balayent `src/app/[lang]` et `src/components`. Elles ratent ce qui vit au-dessus du segment de langue : `app/not-found.js` est restée en français jusqu'au bout du chantier pour cette seule raison. Pour un balayage complet :

```bash
find src -name "*.js" | grep -vE "^src/lib|^src/proxy"
```

**Méthode pour la suite** — pour chaque fichier :

```bash
node scripts/extract-i18n.mjs <fichier>     # inventaire des chaînes
# ajouter les clés dans fr/ puis en/
# convertir le fichier
node scripts/check-i18n.mjs                 # parité + t déclaré + clés connues
```

Attention : l'extracteur signale quelques faux positifs (texte dans les commentaires JSX) et ne voit pas les chaînes construites dynamiquement.

## État du lint

Le chantier n'a introduit **aucune** erreur ESLint. Comparaison faite sur un worktree git à HEAD :

| | HEAD | Maintenant |
|---|---|---|
| Total erreurs | 171 | **73** |
| `react/no-unescaped-entities` | 129 | **33** |

Les 96 apostrophes en moins sont un effet direct de la traduction : le texte français a quitté le JSX pour les dictionnaires. Les 33 qui restent sont dans le code mort listé plus haut et dans les commentaires JSX.

Les avertissements `exhaustive-deps` sont revenus à leur compte d'origine : les quatre que la conversion avait introduits ont été traités un par un (cf. les pièges ci-dessus), pas silencés en bloc.

Les 73 erreurs restantes viennent des nouvelles règles du compilateur React (`react-hooks/immutability`, `set-state-in-effect`, `static-components`, `refs`, `purity`). Elles sont **toutes préexistantes** et concernent le comportement des composants, pas la traduction : les corriger est un chantier distinct, avec un vrai risque de régression fonctionnelle.
